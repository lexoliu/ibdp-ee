\section{Introduction}

Modern programming languages face a fundamental trade-off in memory management: explicit control versus automated safety. Languages like C and Rust demand manual memory management, offering precise control but requiring careful programming to avoid crashes and security vulnerabilities. In contrast, garbage-collected languages like Java and Go automate memory reclamation, reducing bugs but potentially introducing runtime overhead that affects application performance.

While garbage collection theory is well-established, empirical studies comparing GC and non-GC languages often conflate multiple performance factors. This research specifically isolates the impact of garbage collection by implementing algorithmically identical services across three strategically chosen languages: Rust (AOT-compiled, manual memory management), Go (AOT-compiled, garbage collected), and Java (JIT-compiled, garbage collected). This selection enables controlled comparison across both memory management strategies (manual vs. GC) and compilation approaches (AOT vs. JIT) to answer: \textbf{How do performance characteristics vary between GC and non-GC languages?}

The study evaluates three workload categories—compute-intensive, serialization, and allocation-heavy key-value operations—measuring throughput, latency, and memory consumption under controlled conditions. This approach provides evidence-based insights for developers making language selection decisions in performance-critical applications.

\section{Background: Memory Management in Programming Languages}

\subsection{Memory Management Fundamentals}

Memory management shapes how programs allocate, reuse, and eventually release memory. Most languages separate stack and heap usage. Stack frames hold local variables and disappear automatically when a function returns, so programmers rarely intervene. Heap allocations last longer and require either explicit control (as in C or Rust) or a runtime that reconciles unused objects on the developer's behalf.

Understanding the differences between stack and heap memory is crucial for analyzing how programming languages manage memory. In the following sections, we will explore how heap memory is managed through manual techniques and automatic algorithms such as garbage collection.

\subsection{The Challenge of Manual Memory Management}

Early high-level languages such as C and C++ placed all responsibility for heap lifetime on the programmer. The approach delivers raw speed, yet common mistakes—memory leaks, dangling pointers, or double frees—can crash applications or open security holes. These recurring issues motivated automated schemes that keep the performance benefits while avoiding the sharpest edges.

\subsubsection*{Manual Memory Management Examples in C}

\begin{lstlisting}[language=C, caption=Memory Leak Example, style=mystyle]
#include <stdlib.h>

void memory_leak() {
    int* data = (int*) malloc(100 * sizeof(int));
    // Function ends without freeing 'data'
    // This memory remains allocated but inaccessible
}
\end{lstlisting}

\subsection{The Evolution to Automatic Memory Management}

As software systems grew in complexity, the burden of manual memory management became increasingly problematic. This led to the development of automatic memory management techniques that could reliably handle memory allocation and deallocation without programmer intervention. Two primary approaches emerged: reference counting and tracing garbage collection.

\subsubsection{Reference Counting: A First Step}

Reference counting keeps a per-object counter that increments with new references and decrements as they disappear. It spreads reclamation cost across program execution, yet cycles remain a weak point: two objects that point to each other never reach zero and therefore leak.

\subsection{Tracing Garbage Collection: A Comprehensive Solution}

Tracing collectors treat the heap as a graph rooted in stack and global references. They mark every reachable object and reclaim whatever remains, naturally handling cycles and most real-world allocation patterns.

\subsubsection{Mark-and-Sweep: The Archetypal Tracing Algorithm}

Mark-and-sweep alternates two passes. A mark phase follows pointers from the roots to label live objects; a sweep phase scans memory and frees anything unmarked. Modern collectors build on this template with generational heaps or concurrent marking, but the core intuition is unchanged.

\subsubsection{Modern Concurrent Collection Techniques}

Contemporary garbage collectors employ sophisticated techniques to minimize application disruption:

\textbf{Tri-color Invariant and Write Barriers}: Concurrent collectors use a tri-color marking scheme where objects are classified as white (unmarked), gray (marked but not scanned), or black (marked and scanned). The tri-color invariant ensures no black object directly references a white object, maintained through write barriers that intercept pointer updates during concurrent marking phases.

\textbf{Stop-the-World vs. Concurrent Phases}: Modern collectors minimize stop-the-world (STW) pauses by performing most work concurrently with application threads. Only critical phases like root scanning and final marking require STW pauses, typically lasting microseconds rather than milliseconds.

\textbf{Mutator Utilization and Heap Sizing}: The mutator utilization represents the fraction of CPU time available to application code versus garbage collection overhead. Larger heap sizes reduce collection frequency but increase pause times, while smaller heaps increase collection overhead but maintain shorter pauses. This trade-off significantly impacts both throughput and latency characteristics.

\subsection{The Performance Overhead of Garbage Collectors}
"No silver bullet" applies here as well: removing manual memory bugs means accepting some runtime cost. Garbage collectors can introduce brief pauses, reserve extra heap space, and consume CPU cycles to locate dead objects. Quantifying when those effects matter is the empirical focus of the remainder of this essay.

\section{Literature Review}


\subsection{Historical and Contemporary Studies on Garbage Collection}

The evolution of garbage collection has progressed from early concepts \citep{mccarthy1960lisp} to sophisticated modern algorithms addressing real-time constraints \citep{baker1978real}. Wilson's comprehensive survey \citep{wilson1992garbage} established foundational understanding of different collection strategies, while modern systems implement concurrent approaches like the G1 collector \citep{detlefs2004concurrent} to minimize application disruption.

Rigorous performance evaluation methodology has become increasingly important in garbage collection research. \citet{blackburn2006dacapo} established standard benchmarking practices for Java performance analysis, while \citet{georges2007statistically} demonstrated the necessity of statistical rigor in performance evaluation. \citet{kalibera2013rigorous} further refined benchmarking methodologies to ensure reproducible and meaningful results within reasonable time constraints.

Memory management approaches have diversified beyond traditional garbage collection. Conservative collection techniques \citep{boehm1988conservative} demonstrated the feasibility of automatic memory management in uncooperative environments, while ownership type systems \citep{clarke1998ownership} provided static guarantees about memory safety. Modern languages like Rust \citep{matsakis2014rust} leverage these concepts to achieve memory safety without runtime overhead, creating an interesting comparison point for garbage-collected languages.

\subsection{Gap in Existing Research}

Despite decades of progress in garbage collection theory and engineering, there remains a shortage of experimental work that focuses on isolating GC overhead in realistic, end-to-end application workloads. Prior studies often rely on microbenchmarks or compiler-level analysis, which are valuable but do not directly inform practitioners developing web services or distributed systems today. In addition, much of the literature predates modern concurrent and low-latency collectors, making their conclusions less representative of current environments.

Therefore, this project seeks to contribute by:
\begin{itemize}
    \item Narrowing scope to compare GC vs. manual memory management in languages with broadly similar compilation strategies (Rust, Go, Java).
    \item Using application-level workloads (echo server, key-value store, JSON/serialization tasks, prime computation) rather than synthetic allocation loops.
    \item Reporting not only throughput and latency, but also memory consumption trends, which are underexplored in existing studies.
\end{itemize}

\section{Methodology}
\label{sec:methodology}

\subsection{Experimental Setup}

The experimental design compared three languages representing different compilation and memory management strategies:

\begin{itemize}
    \item \textbf{Rust}: AOT-compiled with manual memory management, providing a baseline for deterministic performance
    \item \textbf{Go}: AOT-compiled with concurrent garbage collection, isolating GC overhead from JIT effects
    \item \textbf{Java}: JIT-compiled with generational garbage collection, representing managed runtime environments
\end{itemize}

This selection enables controlled analysis by separating garbage collection effects from compilation strategy effects, while covering the most common approaches in modern systems programming.

\subsection{Framework Selection Strategy}

To represent realistic production scenarios, we selected industry-recommended mature web frameworks for each language: Rust uses Axum (a high-performance async web framework), Go uses Chi (a lightweight HTTP router), and Java uses Spring Boot WebFlux (reactive web framework). This approach represents the typical technology stacks developers encounter in real-world service development.

Our evaluation target is the combined performance of language + typical framework, rather than pure language runtime performance. This design choice prioritizes external validity (ecological validity) over internal validity, as it better reflects the practical considerations developers face when selecting languages for production services.

\subsection{Runtime Configuration and Memory Management}

To ensure fair comparison, we used default configurations for each language runtime, reflecting typical production deployments:

\textbf{Java (OpenJDK 21)}: Used the default G1 garbage collector with generational collection enabled. No explicit GC tuning parameters were specified, allowing the JVM to auto-tune heap sizes and collection thresholds based on available system memory. This represents the out-of-box experience most developers encounter.

\textbf{Go (1.22)}: Employed default garbage collection settings with \texttt{GOGC=100} (target 100\% heap growth before collection) and \texttt{GOMAXPROCS} set to match available CPU cores. Go's concurrent collector uses tri-color marking with write barriers, performing most collection work concurrently with minimal STW pauses.

\textbf{Rust (1.80)}: Used the default system allocator with no special configuration. Rust's ownership system enables deterministic memory management without garbage collection overhead, providing predictable allocation and deallocation patterns through compile-time lifetime analysis.

Benchmarks were executed in two complementary environments to capture both on-device and hosted deployments:

\begin{itemize}
    \item \textbf{Local workstation (baseline)}: MacBook Pro with an Apple M2 Max (12 performance + 4 efficiency cores) and 32~GB unified memory running macOS 15.6. The Go 1.22 toolchain, Rust 1.80 (cargo), and OpenJDK~21/Spring Boot~3.3.3 were installed natively. Both the service under test and the \texttt{k6} client executed on this host for baseline measurements.
    \item \textbf{Aliyun hosted environment}: Tokyo region deployment managed by the benchmark harness. The load generators ran on a dedicated 2~vCPU / 4~GB ECS instance (client), while services were launched on an 8~vCPU / 32~GB ECS instance (server). The same language toolchains were provisioned via the project scripts to ensure parity with the local setup.
\end{itemize}

For each run the harness ensured exclusive access by stopping any previously running service, freeing bound ports, and resetting the manager state before the next language started. Local runs bound to \texttt{127.0.0.1:8080}; cloud runs used the manager-reported public endpoint with identical health checks and orchestration logic.

\subsection{Load Generation and Metrics}

Workloads were stressed using the \texttt{k6} load testing framework in \texttt{normal} mode:

\begin{itemize}
    \item Virtual Users (VUs): 64 across all experiments
    \item Duration: 10 minutes per attempt, matching the harness default for \texttt{normal} mode
    \item Repeats: two sequential attempts per workload, with the first run serving as a pre-warm phase and the second run providing the measurement data
    \item Base URL: \texttt{http://127.0.0.1:8080} for local runs and the manager-advertised service host for Aliyun runs
\end{itemize}

The pre-warm procedure was essential for ensuring fair comparison, particularly for Java's JIT compiler which requires initial execution to optimize hot code paths. This two-phase approach eliminated JIT warm-up effects from the measurements while capturing steady-state performance characteristics.

Each test produced JSON-formatted time-series data capturing:
\begin{itemize}
    \item \textbf{Throughput (requests/sec)} from \texttt{http\_reqs}
    \item \textbf{Median Latency P50 (ms)} from \texttt{http\_req\_duration} - chosen as a robust central tendency measure less sensitive to outliers than mean latency
    \item \textbf{Failure Rate} from \texttt{http\_req\_failed}
\end{itemize}

In addition, memory consumption was sampled once per second using the \texttt{ps} command to record RSS (resident set size). These data were stored in CSV for later analysis.

\subsection{Data Analysis}

For each workload-language combination:
\begin{enumerate}
    \item Time-series data were aligned to a common start time.
    \item Mean throughput, median latency, and peak memory were computed.
    \item Comparative plots were generated for each workload group: throughput, latency, and memory trends.
\end{enumerate}

This analysis design enables both cross-language comparison (e.g., Rust vs. Go under \texttt{/kv/set}) and intra-language workload scaling (e.g., Java across prime vs. KV).

For each workload, we compare throughput (requests per second), median latency (P50, ms), and memory consumption (RSS, MB) across Java, Go, and Rust implementations.

\subsection{Prime Workload: Compute-Intensive, Minimal Allocation}

The prime number benchmark revealed the most dramatic performance differences between languages. Rust achieved the highest throughput at 32,500 requests per second with a median latency of 1.9ms, while Go performed comparably at 30,800 req/s and 2.0ms median latency. Java, however, significantly underperformed with only 11,800 req/s throughput and 5.3ms median latency—representing a 63\% reduction in throughput compared to Rust and 2.7× higher latency.

Critically, this performance gap occurs in a workload with minimal memory allocation, indicating that garbage collection is not the primary bottleneck. Instead, the results point to fundamental JVM runtime overhead including JIT compilation costs, object model inefficiencies, and runtime safety checks that impact even allocation-free computational workloads.

\subsection{Light Workload: Serialization and Moderate Allocation}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.9\linewidth]{../Benchmark/linux_results/plots/comparison_light.png}
    \caption{Performance comparison in Light workload showing convergent performance across languages with minimal GC impact.}
    \label{fig:light-performance}
\end{figure}

The Light workload, comprising echo, JSON serialization, and JSON-to-XML conversion tasks, produced remarkably convergent results across all three languages. All implementations achieved approximately 20,000 requests per second with median latencies between 1.5-1.6ms, representing less than 7\% variation between languages.

This convergence is particularly significant because it demonstrates that under moderate allocation pressure—where serialization creates temporary objects—garbage collection overhead is minimal. Java's performance recovered dramatically from the Prime workload, achieving slightly higher throughput (20,100 req/s) than both Rust and Go (19,900 req/s each), suggesting that the JVM's optimizations become effective when handling I/O-bound operations with moderate object creation.

Latency characteristics remained consistent across languages, with p95 latencies ranging from 3.8-4.7ms, indicating that modern garbage collectors like Go's concurrent GC introduce negligible pause times under typical web service workloads.

\subsection{KV Workload: Allocation-Heavy, Persistent State}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.9\linewidth]{../Benchmark/linux_results/plots/comparison_kv.png}
    \caption{Performance comparison in KV workload showing competitive performance across all languages with minimal GC impact and stable memory usage.}
    \label{fig:kv-performance}
\end{figure}

The KV workload, implementing GET/SET/DELETE operations on a persistent key-value store, was designed to stress memory allocation patterns through frequent object creation and map modifications. Contrary to expectations about garbage collection overhead under allocation pressure, all three languages demonstrated remarkably similar performance:

\begin{itemize}
    \item \textbf{Rust}: 23,200 req/s throughput, 1.3ms median latency, 0.92MB memory
    \item \textbf{Go}: 23,100 req/s throughput, 1.3ms median latency, 0.96MB memory
    \item \textbf{Java}: 22,900 req/s throughput, 1.4ms median latency, 1.02MB memory
\end{itemize}

The performance convergence is striking—less than 1.3\% variation in throughput and minimal median latency differences even under the most allocation-intensive workload. Memory consumption remained remarkably stable and low across all languages, ranging from 0.92-1.02MB, suggesting efficient memory management regardless of the underlying strategy (manual vs. garbage collected).

This result challenges conventional assumptions about garbage collection performance penalties and demonstrates that modern concurrent garbage collectors can effectively handle allocation-heavy workloads without significant overhead.

\subsection{Cross-Workload Analysis}

The benchmark results reveal three key patterns that challenge conventional assumptions about garbage collection performance:

\begin{enumerate}
    \item \textbf{Workload-dependent performance characteristics}: Java's performance varied dramatically by workload type—underperforming significantly in compute-intensive Prime (63\% lower throughput) but achieving competitive or superior performance in I/O-bound Light and KV workloads.
    
    \item \textbf{Minimal garbage collection overhead}: Go consistently matched Rust's performance across all workloads, with differences typically under 5\%. Even Java showed comparable performance in allocation-intensive scenarios, contradicting expectations about significant GC penalties.
    
    \item \textbf{Runtime overhead dominates GC overhead}: The largest performance gaps occurred in allocation-free workloads, indicating that JVM runtime characteristics (JIT compilation, object model, runtime checks) contribute more to performance differences than garbage collection mechanisms.
\end{enumerate}

These findings suggest that the decision between garbage-collected and manually-managed languages should prioritize workload characteristics and runtime behavior over theoretical concerns about GC pause times, particularly given the efficiency of modern concurrent garbage collectors.

\section{Discussion}

\subsection{Research Process and Challenges}

Ensuring implementation consistency across languages presented the primary methodological challenge. Each language was implemented using its most popular web framework (Spring Boot for Java, standard library for Go, and standard library for Rust) with deliberately basic implementations to minimize framework-specific optimizations that could confound results.

Interestingly, the Linux server environment showed much more stable behavior than initially expected. All three languages demonstrated remarkably low and stable memory consumption (under 1.1MB across all workloads), which contrasts with earlier local testing experiences where Java required significant heap tuning. This suggests that the server environment and workload characteristics were well within the memory management capabilities of all tested languages.

\subsection{Critical Turning Points and Research Evolution}

This research underwent several pivotal decisions that fundamentally shaped both methodology and interpretation:

\textbf{Turning Point 1: Aliyun Cloud Deployment Decision}
Initially, benchmarks were conducted locally on macOS. The decision to deploy on Aliyun Linux servers arose from concerns about local environment variability and the need for production-representative conditions. This shift proved transformative—the cloud environment revealed much more stable memory behavior than local testing, where Java had exhibited memory pressure requiring heap tuning. The cloud results showed remarkably low memory usage across all languages (under 1.1MB), fundamentally changing our interpretation from "Java requires significant memory overhead" to "all modern languages can be quite memory-efficient under typical workloads."

\textbf{Turning Point 2: JVM Warm-up Strategy}
Early Java results showed extremely poor performance until we implemented a two-phase testing approach with explicit warm-up runs. This methodological adjustment was crucial for fair comparison, as it separated JIT compilation effects from steady-state performance. However, it also revealed that the warm-up requirement itself represents a practical limitation of Java in scenarios requiring immediate performance (e.g., serverless computing, short-lived processes).

\textbf{Turning Point 3: Go vs. Rust Performance Convergence}
The most surprising finding was Go's near-parity with Rust across all workloads. Initial expectations, based on theoretical GC overhead concerns, predicted Rust would significantly outperform Go, especially under allocation pressure. The reality of negligible differences (<5\% variation) forced a fundamental reframing of the research question from "How much overhead does GC impose?" to "Why is modern GC overhead so minimal?"

\textbf{Turning Point 4: Java's Workload-Dependent Performance}
Java's dramatic performance variation—from 63\% slower in Prime to competitive in Light/KV workloads—revealed that runtime overhead, not GC overhead, was the dominant factor. This insight shifted focus from garbage collection mechanisms to broader runtime architecture considerations, fundamentally altering the conclusions about when and why to choose different languages.

Each turning point required methodological adjustments and interpretive reframing, ultimately producing findings that challenge conventional wisdom about garbage collection performance in realistic application scenarios.

\subsection{Unexpected Findings and Performance Insights}

The results fundamentally challenge common assumptions about garbage collection performance impact:

The most striking finding was the minimal performance difference between garbage-collected and manually-managed languages under realistic workloads. Go consistently matched Rust's performance across all scenarios, while Java showed competitive performance in I/O-bound tasks despite significant underperformance in pure computation.

\begin{itemize}
    \item \textbf{Modern GC Efficiency}: Go's concurrent garbage collector introduced negligible overhead even under allocation-heavy workloads, suggesting that theoretical concerns about GC pauses may be overstated for real-world applications.
    \item \textbf{Runtime vs. GC Overhead}: Java's poor performance in allocation-free Prime workloads (63\% throughput reduction) indicates that JVM runtime characteristics dominate performance differences rather than garbage collection overhead.
    \item \textbf{Workload-Dependent Performance}: The dramatic variation in Java's relative performance across workloads (from 63\% slower in Prime to competitive in Light/KV) suggests that language selection should be based on specific use case requirements rather than general assumptions.
    \item \textbf{Memory Management Efficiency}: All languages maintained stable, low memory footprints (0.9-1.1MB), indicating that modern memory management strategies are efficient regardless of manual vs. automatic approaches.
\end{itemize}

These findings suggest that garbage collection overhead is less significant than commonly believed, and that developer productivity and ecosystem considerations may be more important factors in language selection for most applications.

\subsection{Methodological Considerations: Framework vs. Pure Language Performance}

This study deliberately chose realistic web frameworks over minimal implementations to maximize ecological validity. We considered the trade-off between "minimal framework vs. realistic framework" approaches and selected realistic frameworks because they better represent the environment developers actually work in.

This means our results may include framework-specific overhead in addition to language runtime characteristics, but this represents an unavoidable aspect of real-world service development. The performance differences observed reflect the combined ecosystem performance (language + typical framework + standard libraries) that practitioners encounter, rather than theoretical language capabilities in isolation. This approach provides more actionable insights for technology selection decisions, though it may conflate framework efficiency with underlying language performance in some cases.

\subsection{Limitations and Future Work}

This study's laboratory setting may not fully represent real-world deployment conditions where network latency, concurrent users, and varying hardware configurations could alter performance characteristics. The controlled environment, while necessary for isolating GC effects, abstracts away many production complexities that influence language selection decisions.

Future research should investigate performance under production-like conditions including:
\begin{itemize}
    \item Network-distributed client-server architectures with realistic network latency
    \item Varying concurrent load patterns that better simulate user behavior
    \item Different hardware configurations and resource constraints
    \item Extended runtime periods to capture long-term GC behavior and memory fragmentation effects
\end{itemize}

\subsection{Real-World Engineering Implications}

The findings provide actionable insights for software engineering teams:

\begin{itemize}
    \item \textbf{Microservices Architecture}: The performance parity between Go and Rust suggests that GC overhead should not be a primary concern for most microservice architectures. Go's development ergonomics may outweigh minimal performance differences.
    \item \textbf{Compute-Intensive Applications}: Java's significant underperformance in computational workloads makes it less suitable for pure algorithmic or mathematical applications, where Rust or Go would be preferred.
    \item \textbf{Resource-Constrained Environments}: The low memory usage across all languages (under 1.1MB) indicates that modern applications can be quite efficient regardless of memory management strategy.
    \item \textbf{Performance vs. Productivity Trade-offs}: Given minimal GC overhead, teams can prioritize language ecosystem, developer experience, and tooling over theoretical performance concerns for most applications.
\end{itemize}

\section{Conclusion}

This research evaluated the performance impact of garbage collection by comparing Rust (manual memory management), Go (concurrent GC), and Java (generational GC) across compute-intensive, serialization, and allocation-heavy workloads on Linux servers. The experimental evidence reveals several key findings that challenge conventional assumptions about garbage collection overhead:

\begin{itemize}
  \item \textbf{Minimal GC overhead in practice}: Go consistently matched Rust's performance across all workloads (typically within 5\% variation), demonstrating that modern concurrent garbage collectors impose negligible runtime costs even under allocation pressure.
  \item \textbf{Runtime overhead dominates GC overhead}: Java's significant underperformance in allocation-free workloads (63\% throughput reduction in Prime benchmark) indicates that JVM runtime characteristics contribute more to performance differences than garbage collection mechanisms.
  \item \textbf{Workload-dependent performance characteristics}: Language performance varied dramatically by workload type, with Java achieving competitive performance in I/O-bound scenarios despite poor computational performance, suggesting that application characteristics should drive language selection decisions.
  \item \textbf{Efficient memory management across strategies}: All languages maintained remarkably low and stable memory footprints (0.9-1.1MB), indicating that both manual and automatic memory management approaches can be highly efficient in practice.
\end{itemize}

These findings suggest that theoretical concerns about garbage collection performance penalties may be overstated for real-world applications. Developer productivity, ecosystem maturity, and specific workload requirements should be prioritized over assumptions about GC overhead when selecting programming languages for modern software systems.

Future research should investigate longer-running applications, memory-intensive workloads, and production deployment scenarios to further validate these findings across diverse operational contexts.
