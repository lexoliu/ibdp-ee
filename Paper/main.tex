\subsection{Research Question and Causal Framework}

\subsubsection{Primary Research Question}
\textbf{RQ1 (Main):} In realistic and synthetic tasks, do GC and non-GC languages show statistically significant and engineering-meaningful differences in p95/p99 latency, throughput, and memory footprint?

\textbf{RQ2 (Mechanism):} How do these differences vary with object lifetime distribution, concurrency level, load intensity, and allocation strategy?

\subsubsection{Causal Thinking}
We frame this as a causal inference problem where:
\begin{itemize}
    \item \textbf{Treatment:} Use of GC $\rightarrow$ runtime mechanisms (write barriers/concurrent marking/pauses) $\rightarrow$ instruction and cache behavior $\rightarrow$ latency/throughput/memory
    \item \textbf{Confounders:} Algorithm/library implementation, compilation optimization, I/O and networking $\rightarrow$ controlled through isomorphic implementation, unified libraries and compilation flags, I/O isolation
\end{itemize}

\subsubsection{Hypotheses}
\begin{itemize}
    \item \textbf{H0 (Null):} Under equivalent loads, GC and non-GC languages show no significant difference in p95 latency and throughput (difference $< \delta$)
    \item \textbf{H1 (Alternative):} GC languages introduce statistically and practically significant differences ($\geq \delta$)
\end{itemize}

Equivalence boundaries $\delta$ are set to $\pm$10\% for latency and $\pm$7\% for throughput.

\subsection{Experimental Design}

\subsubsection{Variables}

\paragraph{Independent Variables (Factor Design)}
\begin{itemize}
    \item \textbf{T:} Memory management paradigm (2 levels): non-GC (Rust) vs GC (Go)
    \item \textbf{L:} Load intensity (3 levels): Low (~40\% saturation) / Medium (~70\%) / High (~90-95\%)
    \item \textbf{W:} Task type (4 tiers): C0 pure compute / Micro / Meso / Macro
    \item \textbf{C:} Concurrency (2 levels): Single-thread (or minimal concurrency) / High concurrency (CPU×2)
    \item \textbf{S:} Allocation strategy (2 levels): Pre-allocated/pooled vs temporary allocation
\end{itemize}

\paragraph{Dependent Variables}
\begin{itemize}
    \item \textbf{Primary:} p95, p99 latency; steady-state throughput (RPS/QPS)
    \item \textbf{Secondary:} RSS peak/steady-state, working set size, cycles/op, cache miss\%, GC count and pause distribution (GC group)
\end{itemize}

\paragraph{Control Variables}
Hardware/OS fixed; CPU core binding; unified compilation flags (Rust -O3/LTO, Go version locked); I/O isolation for Micro/C0 tests.

\subsection{Task Suite}

Our benchmark suite implements identical algorithms across languages with four hierarchical categories:

\subsubsection{C0 Pure Compute (Negative Control)}
\begin{itemize}
    \item \textbf{C0a:} Vector dot product/reduction with pre-allocated large arrays, zero allocation
    \item \textbf{C0b:} Vectorizable vs branch-intensive computation (still zero allocation)
    \item \textbf{C0c:} FFT/convolution with pre-allocated work area
    \item \textbf{C0d:} Control version switching between "pre-allocated/pooled" and "per-step temporary buffer" on same algorithm
\end{itemize}

\subsubsection{Micro (Memory Behavior Isolation)}
\begin{itemize}
    \item \textbf{A1:} Short-lived small object burst (16-128B, escape control)
    \item \textbf{A2:} Long-lived set + tidal growth (live set slowly rises)
    \item \textbf{A3:} Random graph traversal (pointer chasing + write barrier cost)
    \item \textbf{A4:} String parsing/concatenation (temporary object flood)
\end{itemize}

\subsubsection{Meso (Medium Scale)}
\begin{itemize}
    \item \textbf{B1:} Batch processing transformation (CSV/JSON→transform→JSON)
    \item \textbf{B2:} Multi-producer multi-consumer queue (allocation→reclaim concurrent paths)
\end{itemize}

\subsubsection{Macro (End-to-End Web)}
\begin{itemize}
    \item \textbf{C1:} Echo (minimal framework path)
    \item \textbf{C2:} Static file serving
    \item \textbf{C3:} JSON API (complex serialization)
    \item \textbf{C4:} Template rendering (server-side HTML generation)
    \item \textbf{C5:} Database query simulation
\end{itemize}

Each task provides both \textbf{S} allocation strategies (pre-allocated/temporary); endpoints and parameters unified across languages.

\subsection{Experimental Design}
Our experiment follows a factorial design with the following factors:

\begin{itemize}
    \item \textbf{Independent variables:} 
    \begin{itemize}
        \item Memory management paradigm (GC vs non-GC)
        \item Load intensity (low, medium, high)
        \item Task type (C0 pure compute, Micro, Meso, Macro)
        \item Concurrency level (single-thread vs multi-thread)
        \item Allocation strategy (preallocated vs temporary)
    \end{itemize}
    \item \textbf{Dependent variables:} 
    \begin{itemize}
        \item Latency (p50, p95, p99)
        \item Throughput (RPS)
        \item Memory footprint (RSS)
        \item CPU cycles per operation, cache misses
        \item GC-specific metrics (pause time, allocation rate)
    \end{itemize}
    \item \textbf{Control variables:} Identical hardware, operating system, compiler optimization levels, networking stack, and benchmarking tools.
\end{itemize}

Each configuration was run in randomized order, with warm-up (30s), steady (120–180s), and overload (60s) phases. Runs were repeated $N \geq 20$ times to ensure statistical power. Statistical tests include Mann–Whitney U for non-parametric comparison, TOST equivalence tests, and Benjamini–Hochberg FDR correction for multiple comparisons.

% NEW: C0 Workloads
\subsection{C0 Pure Compute Workloads}
To validate the experimental design, we include negative control tasks where no memory allocation occurs:
\begin{itemize}
    \item Vector dot product and reduction (zero allocation)
    \item FFT and convolution with preallocated workspace
    \item Branch-heavy compute kernels (to compare branch prediction vs allocation cost)
    \item Allocation strategy contrast (preallocated vs per-iteration temporary buffers)
\end{itemize}

We expect GC and non-GC languages to show \emph{equivalent} performance in these tasks.

\section{Discussion}
While Rust's compile-time memory guarantees and zero-cost abstractions make it ideal for predictable performance, Go demonstrates that well-engineered garbage collectors can remain competitive, especially when memory pressure is low. 

% NEW: Mechanism discussion
Our negative control (C0) confirmed that differences are negligible when allocation is absent, validating the attribution of observed differences in Micro and Macro workloads to memory management. 
GC pauses and write barriers explain the higher tail latencies under allocation-intensive scenarios, while throughput often remains similar due to concurrent GC designs. 

\section{Conclusion}
This research evaluated the performance trade-offs between garbage-collected (Go) and manually-managed (Rust) languages using real-world compute benchmarks. The experimental evidence suggests that:

\begin{itemize}
  \item Garbage collection overhead is negligible in compute-intensive scenarios with low allocation frequency
  \item Rust offers better theoretical control but does not always yield drastic performance gains
  \item Go provides sufficient performance for many real-world tasks, simplifying development without major cost
\end{itemize}

Future work may extend to IO-bound and concurrency-heavy scenarios, where memory pressure and GC activity are more variable.
