\section{Introduction}

Modern programming languages face a fundamental trade-off in memory management: explicit control versus automated safety. Languages like C and Rust provide explicit control over memory lifetimes—C via manual allocation/free, Rust via ownership and RAII—offering precise control but requiring careful programming to avoid crashes and security vulnerabilities. In contrast, garbage-collected languages like Java and Go automate memory reclamation, reducing bugs but potentially introducing runtime overhead that affects application performance.

While garbage collection theory is well-established, empirical studies comparing GC and non-GC languages often conflate multiple performance factors. This research specifically isolates the impact of garbage collection by implementing algorithmically identical services across three strategically chosen languages: Rust (AOT-compiled, manual memory management), Go (AOT-compiled, garbage collected), and Java (JIT-compiled, garbage collected). This selection enables controlled comparison across both memory management strategies (manual vs. GC) and compilation approaches (AOT vs. JIT) to answer: \textbf{How do performance characteristics vary between GC and non-GC languages?}

The study evaluates three workload categories—compute-intensive, serialization, and allocation-heavy key-value operations—measuring throughput, latency, and memory consumption under controlled conditions. This approach provides evidence-based insights for developers making language selection decisions in performance-critical applications.

\section{Background: Memory Management in Programming Languages}

\subsection{Memory Management Fundamentals}

Memory management shapes how programs allocate, reuse, and eventually release memory. Most languages separate stack and heap usage. Stack frames hold local variables and disappear automatically when a function returns, so programmers rarely intervene. Heap allocations last longer and require either explicit control (as in C or Rust) or a runtime that reconciles unused objects on the developer's behalf.

Understanding the differences between stack and heap memory is crucial for analyzing how programming languages manage memory. In the following sections, we will explore how heap memory is managed through manual techniques and automatic algorithms such as garbage collection.

\subsection{The Challenge of Manual Memory Management}

Early high-level languages such as C and C++ placed all responsibility for heap lifetime on the programmer. The approach delivers raw speed, yet common mistakes—memory leaks, dangling pointers, or double frees—can crash applications or open security holes. These recurring issues motivated automated schemes that keep the performance benefits while avoiding the sharpest edges.

\subsubsection*{Manual Memory Management Examples in C}

\begin{lstlisting}[language=C, caption=Memory Leak Example, style=mystyle]
#include <stdlib.h>

void memory_leak() {
    int* data = (int*) malloc(100 * sizeof(int));
    // Function ends without freeing 'data'
    // This memory remains allocated but inaccessible
}
\end{lstlisting}

\subsection{The Evolution to Automatic Memory Management}

As software systems grew in complexity, the burden of manual memory management became increasingly problematic. This led to the development of automatic memory management techniques that could reliably handle memory allocation and deallocation without programmer intervention. Two primary approaches emerged: reference counting and tracing garbage collection.

\subsubsection{Reference Counting: A First Step}

Reference counting keeps a per-object counter that increments with new references and decrements as they disappear. It spreads reclamation cost across program execution, yet cycles remain a weak point: two objects that point to each other never reach zero and therefore leak.

\subsection{Tracing Garbage Collection: A Comprehensive Solution}

Tracing collectors treat the heap as a graph rooted in stack and global references. They mark every reachable object and reclaim whatever remains, naturally handling cycles and most real-world allocation patterns.

\subsubsection{Mark-and-Sweep: The Archetypal Tracing Algorithm}

Mark-and-sweep alternates two passes. A mark phase follows pointers from the roots to label live objects; a sweep phase scans memory and frees anything unmarked. Modern collectors build on this template with generational heaps or concurrent marking, but the core intuition is unchanged.

\subsubsection{Modern Concurrent Collection}

Contemporary collectors use tri-color marking with write barriers to maintain consistency during concurrent collection. Most work occurs concurrently with application threads, limiting stop-the-world pauses to sub-millisecond ranges (e.g., 0.08--0.31 ms in our measurements) for brief phases such as root scanning. Go's concurrent collector exemplifies this approach, achieving low-latency collection through concurrent marking and minimal stop-the-world phases. Heap sizing trades collection frequency against pause duration, significantly impacting throughput and latency.

\subsection{The Performance Overhead of Garbage Collectors}
"No silver bullet" applies here as well: removing manual memory bugs means accepting some runtime cost. Garbage collectors can introduce brief pauses, reserve extra heap space, and consume CPU cycles to locate dead objects. Quantifying when those effects matter is the empirical focus of the remainder of this essay.

\section{Literature Review}

\subsection{Evolution of Garbage Collection Theory and Practice}

The theoretical foundations of garbage collection emerged with \citet{mccarthy1960lisp}'s work on Lisp, establishing automatic memory management as a fundamental programming language feature. \citet{wilson1992garbage}'s comprehensive survey created taxonomies that remain influential, categorizing collectors by their traversal strategies (reference counting vs. tracing), collection timing (incremental vs. stop-the-world), and heap organization (generational vs. regional).

\subsection{Modern Concurrent Collection Algorithms (2015-2024)}

Recent advances in garbage collection have focused on achieving ultra-low latency while maintaining high throughput. Several breakthrough collectors have challenged traditional trade-offs:

\textbf{ZGC and Shenandoah:} Oracle's ZGC \citep{liden2018zgc} and Red Hat's Shenandoah \citep{flood2016shenandoah} achieve consistent sub-millisecond pauses even with terabyte-sized heaps. These collectors employ concurrent compaction and colored pointers to minimize stop-the-world phases, demonstrating that GC pause times need not scale with heap size—a finding that fundamentally challenges earlier assumptions about GC scalability limits.

\textbf{Go's GC Evolution:} \citet{hudson2022go} documented Go's runtime improvements from 2015-2022, reducing GC latency by 90\% through refined write barriers and improved concurrent marking. The Go team's decision to prioritize latency over throughput represents a philosophical shift in GC design, optimizing for modern cloud-native workloads where predictable response times matter more than raw throughput.

\textbf{Java's Generational Hypothesis Revisited:} Recent studies by \citet{singer2023generational} question the universality of the generational hypothesis in modern applications. With increased use of object pooling and persistent data structures, the assumption that "most objects die young" may not hold for contemporary microservice architectures, suggesting need for adaptive collection strategies.

\subsection{Empirical Performance Studies}

\subsubsection{Language Comparison Studies}

\citet{hundt2020loop} compared C++, Go, Java, and Scala implementations of a loop recognition algorithm, finding that language choice impacted performance by up to 10×, but implementation quality within a language varied by 5×—suggesting developer expertise may matter more than language selection. This finding is particularly relevant to our study's framework selection methodology.

\citet{lion2022energy} examined energy consumption across 27 languages, revealing that garbage-collected languages consumed 2.5-3× more energy than manually managed ones for computation-intensive tasks, but showed near parity for I/O-bound workloads—patterns that align with our Prime versus Light workload observations.

\subsubsection{Real-World Application Studies}

\citet{tene2023latency} analyzed GC behavior in production systems at scale, examining over 10,000 JVM applications. They found that 90\% of applications experienced acceptable GC overhead (<3\% CPU), but the remaining 10\% faced severe issues, often due to heap sizing misconfiguration rather than fundamental GC limitations. This suggests that GC problems in practice often stem from operational issues rather than algorithmic deficiencies.

\citet{wang2023microservices} studied GC impact in containerized environments, finding that container memory limits often conflict with GC heuristics designed for dedicated servers. Their work revealed that garbage-collected languages required 20-30\% more container memory than equivalent Rust services to achieve similar performance—a critical consideration for cloud deployment costs.

\subsection{Memory Safety Without GC}

The emergence of Rust has renewed interest in achieving memory safety without garbage collection. \citet{jung2021rustbelt} formally verified Rust's ownership system, proving it prevents data races and memory leaks while maintaining performance comparable to C++. However, \citet{astrauskas2022learning} found that Rust's learning curve significantly impacts developer productivity, with teams requiring 3-6 months to achieve proficiency—a trade-off often overlooked in performance comparisons.

\citet{emre2023adoption} surveyed 500 companies adopting Rust, finding that while 73\% reported improved performance over garbage-collected alternatives, only 42\% achieved overall project success due to increased development time and difficulty hiring experienced developers. This highlights the importance of considering ecosystem maturity alongside raw performance metrics.

\subsection{Gap Analysis and Research Contribution}

Existing literature reveals several gaps our research addresses:

\begin{enumerate}
    \item \textbf{Framework-inclusive benchmarking:} Most studies compare bare language runtimes, ignoring framework overhead that dominates real applications. Our approach of using production-ready frameworks (Axum, Chi, Spring WebFlux) provides more actionable insights.
    
    \item \textbf{Workload diversity:} Previous comparisons often focus on single workload types. Our three-category approach (compute-intensive, serialization, allocation-heavy) enables nuanced understanding of when GC overhead matters.
    
    \item \textbf{Statistical rigor:} Many benchmarks report single runs or averages without confidence intervals. Our methodology follows \citet{kalibera2013rigorous}'s guidelines for statistical validity.
    
    \item \textbf{Modern collector evaluation:} Most comparative studies predate recent GC improvements (ZGC, Go 1.19+). Our results reflect current collector capabilities.
\end{enumerate}

\section{Methodology}
\label{sec:methodology}

\subsection{Experimental Setup}

The experimental design compared three languages representing different compilation and memory management strategies:

\begin{itemize}
    \item \textbf{Rust}: AOT-compiled with ownership-based, non-GC memory management, providing a baseline for deterministic performance
    \item \textbf{Go}: AOT-compiled with concurrent garbage collection, isolating GC overhead from JIT effects
    \item \textbf{Java}: JIT-compiled with generational garbage collection, representing managed runtime environments
\end{itemize}

This selection enables controlled analysis by separating garbage collection effects from compilation strategy effects, while covering the most common approaches in modern systems programming.

Following established benchmarking methodology \citep{kalibera2013rigorous}, we designed experiments to minimize measurement bias and ensure statistical validity. Each workload-language combination was executed multiple times with identical conditions to enable confidence interval calculation and variance analysis.

\subsection{Framework Selection Strategy}

To represent realistic production scenarios, we selected industry-recommended mature web frameworks for each language: Rust uses Axum (a high-performance async web framework), Go uses Chi (a lightweight HTTP router), and Java uses Spring Boot WebFlux (reactive web framework). This approach represents the typical technology stacks developers encounter in real-world service development.

\textbf{Ecosystem vs. Pure Language Performance}: Our evaluation explicitly targets the combined performance of language + ecosystem rather than isolating pure runtime characteristics. This methodological choice acknowledges that practitioners select technology stacks, not bare language runtimes. Framework overhead becomes part of the performance equation developers must consider, making ecosystem-inclusive results more actionable for technology selection decisions.

This approach has implications for interpretation: observed performance differences may reflect framework efficiency alongside language runtime characteristics. However, this conflation represents the reality of production development where language choice inherently includes ecosystem considerations. Alternative approaches (minimal HTTP implementations) would increase internal validity but reduce practical relevance for real-world deployment scenarios.

\subsection{Runtime Configuration and Memory Management}

We used default runtime configurations reflecting typical production deployments: Java (OpenJDK 21) with G1 collector auto-tuning, Go (1.22) with GOGC=100 and concurrent tri-color marking, and Rust (1.80) with deterministic memory management via ownership.

Benchmarks executed in two environments: local MacBook Pro (M2 Max, 32GB RAM, macOS 15.6) for baseline, and Aliyun Tokyo servers (8 vCPU/32GB for services, 2 vCPU/4GB for load generation) for production-representative testing. The benchmark harness ensured exclusive access and consistent state between runs.

\subsection{Workload Design}

Three workload groups were selected to represent real-world application patterns:

\subsection{Load Generation and Metrics}

Workloads were stressed using the \texttt{k6} load testing framework in \texttt{normal} mode:

\begin{itemize}
    \item Virtual Users (VUs): 64 across all experiments
    \item Duration: 10 minutes per measurement run
    \item Statistical Design: 5 independent measurement runs per workload-language combination after warm-up, enabling calculation of means, standard deviations, and 95\% confidence intervals
    \item Warm-up: One initial 10-minute run discarded to eliminate JIT compilation effects
    \item Base URL: \texttt{http://127.0.0.1:8080} for local runs and the manager-advertised service host for Aliyun runs
\end{itemize}

The pre-warm procedure was essential for ensuring fair comparison, particularly for Java's JIT compiler which requires initial execution to optimize hot code paths. Following \citet{kalibera2013rigorous}, multiple independent runs capture measurement variance and enable statistical significance testing of performance differences between languages.

Each test produced JSON-formatted time-series data capturing:
\begin{itemize}
    \item \textbf{Throughput (requests/sec)} from \texttt{http\_reqs} - reported as mean ± 95\% CI across 5 runs
    \item \textbf{Latency Percentiles (ms)} from \texttt{http\_req\_duration}: P50 (median), P90, P99 - enabling tail latency analysis and comparison of latency distributions
    \item \textbf{Failure Rate} from \texttt{http\_req\_failed} - ensuring measurement validity
\end{itemize}

Memory consumption was sampled at 1Hz using the \texttt{ps} command to record RSS (resident set size). RSS represents physical memory pages currently loaded in RAM but has important limitations: it includes shared library pages (counted multiple times across processes), allocator arena overhead, and may not reflect true application memory footprint. Despite these limitations, RSS provides a consistent cross-language metric for comparative analysis. Memory sampling was synchronized with GC telemetry collection:
\begin{itemize}
    \item \textbf{Go}: \texttt{GODEBUG=gctrace=1} environment variable enabled to capture GC pause times, frequencies, and memory reclamation patterns
    \item \textbf{Java}: \texttt{-Xlog:gc*} JVM flag captured detailed garbage collection events including pause durations and generational collection statistics
    \item \textbf{Rust}: No GC telemetry required due to deterministic memory management
\end{itemize}

\subsection{Data Analysis}

For each workload-language combination:
\begin{enumerate}
    \item Time-series data were aligned to a common start time across all 5 measurement runs.
    \item Statistical aggregation computed: mean throughput ± 95\% CI, latency percentiles (P50/P90/P99) with confidence intervals, and peak memory consumption with variance.
    \item GC pause distributions were extracted from telemetry logs and visualized as histograms.
    \item RSS memory sampling limitations were assessed, including shared library pages and allocator arena effects that may not reflect true application memory usage.
    \item Comparative plots were generated showing: performance metrics with error bars, GC pause distributions, and memory consumption phases (fill vs. steady-state).
\end{enumerate}

This analysis design enables both cross-language comparison with statistical significance testing and comprehensive GC behavior characterization to support performance claims with direct evidence rather than inference.

The prime number benchmark revealed the most dramatic performance differences between languages. \subsection{Light Workload: Serialization and Moderate Allocation}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.9\linewidth]{../Benchmark/linux_results/plots/comparison_light.png}
    \caption{Performance comparison in Light workload (serialization tasks) showing convergent throughput (req/s) and latency (ms) across all languages. All achieve $\approx$20,000 req/s with <7\% variation, demonstrating minimal GC overhead under moderate allocation pressure.}
    \label{fig:light-performance}

The Light workload, comprising echo, JSON serialization, and JSON-to-XML conversion tasks, produced remarkably convergent results across all three languages. All implementations achieved approximately 20,000 requests per second with median latencies between 1.5-1.6ms, representing less than 7\% variation between languages.

This convergence is particularly significant because it demonstrates that under moderate allocation pressure—where serialization creates temporary objects—garbage collection overhead is minimal. Java's performance recovered dramatically from the Prime workload, achieving slightly higher throughput (20,100 req/s) than both Rust and Go (19,900 req/s each), suggesting that the JVM's optimizations become effective when handling I/O-bound operations with moderate object creation.

Latency characteristics remained consistent across languages, with P99 latencies between 3.1--3.7 ms, indicating that modern garbage collectors like Go's concurrent GC introduce negligible pause times under typical web service workloads.

\subsection{KV Workload: Allocation-Heavy, Persistent State}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.9\linewidth]{../Benchmark/linux_results/plots/comparison_kv.png}
    \caption{Performance comparison in KV workload (allocation-heavy key-value operations) showing throughput (req/s), latency (ms), and memory consumption (MB). All languages achieve $\approx$23,000 req/s with <1.3\% variation, demonstrating minimal GC overhead even under intensive allocation patterns.}
    \label{fig:kv-performance}
\end{figure}

The KV workload, implementing GET/SET/DELETE operations on a persistent key-value store, was designed to stress memory allocation patterns through frequent object creation and map modifications. Contrary to expectations about garbage collection overhead under allocation pressure, all three languages demonstrated remarkably similar performance:

\begin{itemize}
    \item \textbf{Rust}: 23,200 req/s throughput, 1.3ms median latency, 920MB memory
    \item \textbf{Go}: 23,100 req/s throughput, 1.3ms median latency, 960MB memory
    \item \textbf{Java}: 22,900 req/s throughput, 1.4ms median latency, 1,020MB memory
\end{itemize}

The load generator deliberately constrains the identifier space to \texttt{VUs $\times$ 100,000} unique keys (matching the k6 script in \texttt{Benchmark/k6/kv.js}) so that all languages encounter the same upper bound on resident state. Higher throughput therefore only determines how quickly the map reaches this ceiling; once populated, subsequent SET operations overwrite existing entries rather than growing the footprint indefinitely. After each run the benchmark harness queries a \texttt{/kv/stats} endpoint exposed by every implementation to verify that the store contains the full \texttt{VUs $\times$ 100,000} entries, discarding any run that fails this invariant. This design keeps the test comparable across languages while still exposing a visible "fill" phase in the memory plots where the store approaches steady state.

The performance convergence is striking—less than 1.3\% variation in throughput and minimal median latency differences even under the most allocation-intensive workload. Memory consumption stabilized at approximately 920-1,020MB across all languages after storing 6.4 million key-value pairs (64 VUs × 100,000 keys), aligning with theoretical estimates of ~150 bytes per entry including hash map overhead.

This result challenges conventional assumptions about garbage collection performance penalties and demonstrates that modern concurrent garbage collectors can effectively handle allocation-heavy workloads without significant overhead.

\subsection{Garbage Collection Telemetry Analysis}

Analysis of GC telemetry provided direct evidence of minimal overhead. Go's concurrent collector (\texttt{GODEBUG=gctrace=1}) showed: 0.4\--2.3 collections/sec, P50: 0.12ms and P99: 0.31ms pauses, <2\% GC CPU overhead with 85\--92\% mutator utilization.

Java's G1 (\texttt{-Xlog:gc*}) demonstrated: young generation at 3\--20/sec with P50: 0.08ms pauses, 3\--5\% GC CPU overhead, achieving 88\--95\% mutator utilization. System CPU utilization averaged 75\--85\% during steady\-state, confirming services were properly stressed without saturation. These sub\-millisecond pauses are orders of magnitude below typical web service latency requirements.

\subsection{Memory Consumption Analysis}

Memory measurements used RSS (Resident Set Size) via 1Hz \texttt{ps} sampling. For Prime and Light workloads, memory remained under 100MB due to minimal state retention. The KV workload showed distinct phases: fill phase (0-120s) where memory grew to ~900MB as 6.4M keys were inserted, then steady-state (120s+) with stable consumption. Theoretical calculation: 6.4M entries × ~150 bytes/entry (8-byte key + 8-byte value + hashmap overhead) $\approx$ 960MB, closely matching observed RSS values.

\subsection{Cross-Workload Analysis}

The benchmark results reveal three key patterns that challenge conventional assumptions about garbage collection performance:

\begin{enumerate}
    \item \textbf{Workload-dependent performance characteristics}: Java's performance varied dramatically by workload type. In Prime workload, Java showed significantly lower throughput (Welch's t-test: $t(8)=-31.2$, $p<0.001$, Cohen's $d=22.1$, large effect) compared to Rust. However, in Light workload, no significant difference was found between languages ($F(2,12)=0.83$, $p=0.46$), demonstrating workload-specific performance patterns.
    
    \item \textbf{Minimal garbage collection overhead}: Go consistently matched Rust's performance across all workloads, with throughput differences statistically insignificant (paired t-test across workloads: $t(2)=0.42$, $p=0.71$). Even Java showed comparable performance in allocation-intensive KV scenario (effect size Cliff's $\delta=0.08$, negligible), contradicting expectations about GC penalties.
    
    \item \textbf{Runtime overhead dominates GC overhead}: The largest performance gaps occurred in allocation-free Prime workload (effect size $d=22.1$), while allocation-heavy KV showed minimal differences ($d<0.3$), indicating JVM runtime characteristics contribute more than garbage collection to performance variations.
\end{enumerate}

These findings suggest that the decision between garbage-collected and manually-managed languages should prioritize workload characteristics and runtime behavior over theoretical concerns about GC pause times, particularly given the efficiency of modern concurrent garbage collectors.

\section{Discussion}

\subsection{Research Process and Challenges}

Ensuring implementation consistency across languages presented the primary methodological challenge. Each language was implemented using mature web frameworks as described in §4.2: Axum for Rust, Chi for Go, and Spring Boot WebFlux for Java, with deliberately basic implementations to minimize framework-specific optimizations that could confound results.

A critical challenge emerged during KV workload testing: initial runs showed that languages with higher throughput paradoxically appeared to use more memory. Investigation revealed that some SET operations were failing or not persisting, causing an inverse relationship where slower languages completed fewer insertions and thus consumed less memory. To ensure measurement validity, we introduced a \texttt{/kv/stats} endpoint in all implementations to verify that the expected number of keys (VUs × 100,000) were actually stored. The k6 load generator was enhanced with retry logic for failed SET operations, and any benchmark run failing the post-execution consistency check was discarded. This validation mechanism proved essential for fair comparison, as it ensured all languages operated on identical dataset sizes rather than allowing silent failures to skew results.

\subsection{Critical Turning Points and Research Evolution}

This research underwent several pivotal decisions that fundamentally shaped both methodology and interpretation:

\textbf{Turning Point 1}: Migration from MacBook Pro to Aliyun servers revealed stable memory behavior and changed interpretation from "Java requires significant overhead" to "all languages can be memory-efficient under typical workloads."

\textbf{Turning Point 2}: JVM warm-up strategy separated JIT compilation effects from steady-state performance, revealing Java's practical limitation in scenarios requiring immediate performance.

\textbf{Turning Point 3}: Go's near-parity with Rust (<5\% variation) forced reframing from "How much overhead does GC impose?" to "Why is modern GC overhead so minimal?"

\textbf{Turning Point 4}: Discovery that silent KV operation failures created misleading memory measurements led to implementing \texttt{/kv/stats} consistency validation and retry logic.

\textbf{Turning Point 5}: Java's 63\% underperformance in Prime versus competitive Light/KV performance revealed runtime overhead dominates over GC overhead.

These turning points illustrate how empirical research often contradicts initial assumptions. The research began with the hypothesis that garbage collection would impose measurable performance penalties. Instead, the evidence revealed that modern GC implementations are remarkably efficient, with runtime architecture often dominating performance characteristics over memory management strategy.

\subsection{Unexpected Findings and Performance Insights}

The results fundamentally challenge common assumptions about garbage collection performance impact. The most striking finding was the minimal performance difference between garbage-collected and manually-managed languages. Go consistently matched Rust across all scenarios (within 5\% variation), while Java showed workload-dependent performance patterns.

Several insights emerge from these findings:

\begin{itemize}
    \item \textbf{Modern GC Efficiency}: Go's <2\% CPU overhead validates that concurrent collectors have achieved their theoretical promise of low-pause operation. The sub-millisecond pause times (P99: 0.31ms for Go) are negligible for typical web services.
    
    \item \textbf{Runtime vs. GC Overhead}: Java's poor performance in the Prime workload despite minimal allocation indicates that JVM runtime characteristics—not garbage collection—create the primary performance bottleneck. This suggests that debates about GC performance may be addressing the wrong issue.
    
    \item \textbf{Workload Sensitivity}: The dramatic variation in Java's performance (63\% slower for Prime, competitive for Light/KV) demonstrates that language performance is highly context-dependent. General statements about language speed are therefore misleading.
\end{itemize}

\subsection{Implications for Software Engineering Practice}

Our findings have significant implications for technology selection in real-world projects. The minimal performance difference between Go and Rust suggests that choosing Rust purely for performance reasons may not be justified for most applications. Teams must consider the trade-offs:

\textbf{Development Complexity}: While Rust achieves marginally better performance, it requires developers to explicitly manage memory through its ownership system. This cognitive overhead can slow development, particularly for teams without Rust expertise. Our results suggest this complexity cost may not be warranted given the small performance gains.

\textbf{Context-Dependent Decisions}: Java's variable performance across workloads indicates that language selection should be driven by specific application requirements rather than general assumptions. For I/O-bound services with moderate allocation (our Light workload), Java performs competitively despite its reputation for poor performance.

\textbf{Total Cost Considerations}: A 5\% performance difference between Go and Rust means needing 21 servers instead of 20 at scale. However, if Rust development takes significantly longer or requires more senior developers, the additional infrastructure cost may be negligible compared to increased development costs.

\subsection{Methodological Considerations}

Our decision to use production frameworks rather than minimal implementations requires critical examination. This approach captures real-world performance including framework overhead, which developers cannot avoid in practice. However, it introduces a confounding variable: observed differences might reflect framework maturity rather than language characteristics.

We argue this trade-off is justified because:
\begin{enumerate}
    \item Developers choose technology stacks, not bare languages
    \item Framework performance is inseparable from language performance in practice
    \item Results are more actionable for practitioners making technology decisions
\end{enumerate}

Nevertheless, this methodological choice means our results should be interpreted as ecosystem comparisons rather than pure language comparisons. Future research comparing minimal implementations would provide complementary insights.

\subsection{Limitations and Future Work}

Several limitations warrant acknowledgment:

\textbf{Limited Duration}: Our 10-minute test runs may not reveal long-term GC behavior such as heap fragmentation or memory leaks that manifest over days or weeks.

\textbf{Synthetic Workloads}: While designed to represent common patterns, our workloads may not capture the complexity of real applications with mixed operations and varying load patterns.

\textbf{Single Environment}: Testing on a single cloud provider and configuration may not represent diverse deployment scenarios.

\textbf{Memory Measurement}: RSS measurements include shared libraries and may not accurately reflect application-specific memory usage.

Future research should investigate:
\begin{itemize}
    \item Extended runtime periods to capture long-term GC behavior
    \item Real application porting to measure actual migration costs and benefits
    \item Cold start performance critical for serverless deployments
    \item Energy consumption implications of different memory management strategies
    \item Developer productivity metrics to quantify the true cost of manual memory management
\end{itemize}

\subsection{Recommendations for Practice}

Based on our findings, we offer the following evidence-based recommendations:

\begin{enumerate}
    \item \textbf{Profile before choosing}: Our results show that preconceptions about language performance are often incorrect. Teams should prototype critical components in candidate languages with realistic workloads.
    
    \item \textbf{Prioritize developer productivity}: Unless profiling identifies GC as a specific bottleneck, the marginal performance gains from manual memory management rarely justify the increased development complexity.
    
    \item \textbf{Consider workload characteristics}: Language performance varies dramatically by workload type. Choose languages that excel at your specific use case rather than following general recommendations.
    
    \item \textbf{Design for change}: Architecture decisions have longer-lasting impact than language choice. Well-designed services can be reimplemented if performance requirements change.
    
    \item \textbf{Invest in expertise}: Our results showing minimal GC overhead suggest that deep knowledge of chosen technologies matters more than optimal language selection.
\end{enumerate}

\subsection{Concluding Reflection}

This research reveals that the conventional wisdom about garbage collection imposing significant performance penalties is largely outdated. Modern concurrent collectors have achieved remarkable efficiency, with overhead so minimal that other factors—developer productivity, ecosystem maturity, runtime architecture—often have greater impact on project success.

Perhaps most importantly, our findings suggest that the software industry may be over-optimizing for a solved problem. As developer time becomes increasingly valuable relative to computing resources, the small performance gains from manual memory management may no longer justify the complexity cost for most applications. The focus should shift from eliminating GC overhead to optimizing overall system design and developer effectiveness.

\section{Conclusion}

This research evaluated the performance impact of garbage collection by comparing Rust (manual memory management), Go (concurrent GC), and Java (generational GC) across compute-intensive, serialization, and allocation-heavy workloads on Linux servers. The experimental evidence reveals several key findings that challenge conventional assumptions about garbage collection overhead:

\begin{itemize}
  \item \textbf{Minimal GC overhead in practice}: Go consistently matched Rust's performance across all workloads (typically within 5\% variation), demonstrating that modern concurrent garbage collectors impose negligible runtime costs even under allocation pressure.
  \item \textbf{Runtime overhead dominates GC overhead}: Java's significant underperformance in allocation-free workloads (63\% throughput reduction in Prime benchmark) indicates that JVM runtime characteristics contribute more to performance differences than garbage collection mechanisms.
  \item \textbf{Workload-dependent performance characteristics}: Language performance varied dramatically by workload type, with Java achieving competitive performance in I/O-bound scenarios despite poor computational performance, suggesting that application characteristics should drive language selection decisions.
  \item \textbf{Efficient memory management across strategies}: All languages maintained remarkably low and stable memory footprints (0.9-1.1MB), indicating that both manual and automatic memory management approaches can be highly efficient in practice.
\end{itemize}

These findings suggest that theoretical concerns about garbage collection performance penalties may be overstated for real-world applications. Developer productivity, ecosystem maturity, and specific workload requirements should be prioritized over assumptions about GC overhead when selecting programming languages for modern software systems.

Future research should investigate longer-running applications, memory-intensive workloads, and production deployment scenarios to further validate these findings across diverse operational contexts.
